    the time the pass ended. It was a memo cache, not a channel. The channel had to be
    BUILT: an identity-keyed `Map<ASTNode, InferredType>` that is never scoped and never
    popped, handed to Context, read by codegen.

    expression at module top level was recorded nowhere at all. The channel is written
    unconditionally.)

    Pa: match guards -- `pattern :when expr` (D26)
    
    A guard narrows a pattern with a boolean the pattern alone cannot express. It is a separate clause, not
    a kind of pattern:
    
        x :when (< x 0)   => "neg"
        [a b] :when (> a b) => "descending"   ;; composes with a destructure
    
    The pattern BINDS, the guard READS those bindings and gates the arm. Codegen ANDs the guard onto the
    pattern condition, in that order and for a reason: an identifier-pattern's condition is
    `(x = matchVar, true)` -- it binds `x` as a side effect -- so the guard, to its right under `&&`, sees
    the binding the pattern just made, and `&&` short-circuits so a false pattern never runs the guard
    against the wrong shape.
    
    D26 rejects the two predicate-shaped syntaxes that already exist in the repo: `(< _ 0)` (what
    03_matching.lisp writes -- ambiguous with a parenthesised destructure `(1 2 3)`) and `(fn [x] ...)`
    (what the design sketch writes -- invents a per-arm lambda). `:when` is unambiguous with no lookup,
    composes with any pattern, and is what Rust/Scala/F# chose.
    
    TWO FRONTEND BUGS, and the PEG one was pre-existing and load-bearing:
    
      - grammar_v2: `:when` needed a token (`WhenModKw`, following the `OfModKw` pattern exactly) and an
        OPTIONAL clause in `matchCase`, labelled guard/body so the two expressions never collide.
    
      - PEG: `x :when true => body` failed to parse ENTIRELY and fell back to a plain list -- which is why
        it reported `'match' is not defined`. `true =>` was parsed as `true = >`: a simple-assignment of the
        operator `>`, because `AssignmentOperatorKw = "="i` happily consumed the `=` of `=>`. D2 ("`=` is not
        an assignment") is applied in grammar_v2 and NOT in PEG, so v2 never had this. Fixed at the root with
        `"="i !">"` -- an assignment has no business eating the arrow token -- which also closes a latent
        divergence that had nothing to do with guards.

    next, per the ruling. `:of` type patterns are still dead, so `x :of String :when ...` does not work yet
    -- surfaced in D26, not absorbed.

    D29 -- the strategic principle. A language construct is DEFINED by a stdlib interface and LOWERED per
    backend, not hardcoded in the code generator. `for :each` was hardcoded to emit `for...of` with no
    protocol behind it, which is why the checker could not read an element type, a user type could not be
    made iterable, and the construct could never move to another backend. The insight that makes this
    cheap: on JS the runtime already IS the protocol (`for...of` calls `[Symbol.iterator]().next()`,
    `function*` is a generator, `async` is a Promise machine) -- so "desugar onto the protocol" means the
    semantics are the interface and the JS lowering is the native form, NOT a while-loop rewrite that would
    uglify the output and move every golden. The protocol lives at the language level precisely so a future
    LLVM backend can lower the same `Iterable<T>` to vtable calls + `llvm.coro.*` while the desugaring is
    written once.

        (definterface Iterator<T> (fn next [] -> T?))
        (definterface Iterable<T> (fn iterator [] -> Iterator<T>))
    
    `next` returns `T?` and `nil` means done -- folding onto D9 (the same optional, forced-unwrap and
    flow-narrowing), not a `{value, done}` record. The `T? <-> {value, done}` bridge is the JS code
    generator's job and lands with generators. `for :each` will require `coll : Iterable<T>` and bind
    `x : T` (Itb); native `T[]`/`String`/`Map` are blanket conformers, as arrays are in C#.

    (nil = done, D30). JS `for...of` looks for `[Symbol.iterator]` and expects a `{value, done}` iterator,

      - a runtime helper `__ll_js_iter(it)` that adapts an l-lang iterator (`next() -> T?`) into a JS one
        (`next() -> {value, done}`), folding D9's nil = done;
      - a `[Symbol.iterator]() { return __ll_js_iter(this.iterator()); }` method, INJECTED by the class
        builder onto any type whose `:implements` names Iterable. One bridge per type.

    to the hand-written case exactly.

        (|| a b)  ->  _7c7c(a, b)
    
    The VALUES were always right — it folds with JS's own `||`. But a shim is a
    CALL, and a call evaluates its arguments before it runs. Short-circuiting is
    not an optimisation detail; it is what these two operators MEAN.
    
    `||` and `&&` are precisely the operators that cannot be overloaded, for the
    same reason they must short-circuit: an overload is a function, and a
    function cannot decline to evaluate its argument. So there was nothing for
    the shim to dispatch to and no reason to pay for the call. Nothing in lib/
    or examples/ overloads them. They now emit native LogicalExpressions.

    shim for emission, so a program whose only `||` is in call position no
    longer carries `_7c7c` at all. Using the operator AS a value (`(map || xs)`)
    still goes through visitIdentifier and still gets the shim.
    
    Value-identical by construction: the shim folds LEFT, and `a || b || c` is
    the same fold.
